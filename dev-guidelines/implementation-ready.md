# 実装前の準備と手戻り防止

Issueを実装し始める前と、設計と食い違ったときだけ読みます。作業の流れは[作業フロー](workflow.md)、設計の入口は[設計書の索引](../docs/design/README.md)です。

## 着手前チェック（Definition of Ready）

次の7つが揃うまで、コードを書き始めません。揃わない項目は、Issueに書いて担当者へ返します（黙って推測で進めない）。

1. **重複がない**: 同じ目的のオープンPR・ブランチが無く、`main` の履歴にも同種の実装が無い。`gh pr list`、`git log origin/main --grep`、対象シンボルの検索で確認する。重複していたら、重複先と差分をIssueに書いて着手を保留し、担当者の整理（継承・クローズ）を待つ。
2. **先行Issueが満たされている**: [実装パケット](../docs/design/README.md)の「先行」が全て `main` に入っている。未統合のPRに依存するなら、(a) そのPRの統合を待つか、(b) 依存PRのブランチを基点にして、PRのbaseをそのブランチへ向ける（[作業フロー](workflow.md)の工程1）。依存PR・基点commitをIssueに書く。
3. **契約が決まっている**: 入出力の型名・フィールド・ファイル形式・保存先が、パケットまたは設計正本に書かれている。無ければ実装ではなく設計の追加が先。担当Issueの実装パケットが[索引](../docs/design/README.md)に無いときも、着手せず、Issueに「パケットが無い」と書いて設計の追加を依頼する。
4. **決定待ちがない**: パケットの「要決定」が、[決定記録](../docs/design/decisions.md)で「確定」「暫定」「実装内」のどれかになっている。記録に無い、または「待ち」の項目は着手しない。「暫定」「実装内」はその案で進めてよいが、確定で変わりうることをPRに書く。
5. **触るファイルが分かっている**: パケットの「触るもの」と「同一ファイルを触るIssue」の表を見て、並行中の他Issueと衝突しないことを確認する。衝突するなら順序をIssueに書く。
6. **テストの置き場が決まっている**: 契約を検証する自動テストの名前案と、自動化できない確認（実GPU・実素材・GUI）の区別がパケットにある。
7. **非目標が読めている**: 今回やらないことを確認し、無関係な整理を混ぜない。

## 実装中に守ること

- **契約を先に固定する**: 型・スキーマ・保存形式の変更を、利用側の実装より先に別のコミットで入れ、契約を検証するテストを先に書く。
- **主張は原典で確認する**: 「mainに無い」「重複している」「テストが通った」は、ファイルの中身・実行結果を読んでから書く。名前の一致やログの断片で判断しない。
- **古い前提を持ち込まない**: 過去のPR・計画・テストが前提にする仕様は、現在の `main` のコードと設計で確認する。仕様が変わっていたら、テストを現行仕様に合わせるのではなく、変更の理由を確認する。
- **設計と実装の差分は同じPRで直す**: 実装を変えたら、該当するパケット・設計正本・`docs/`・宣言コメント・テストも同じPRで更新する。
- **整形は触ったファイルすべてに**: Markdown・JSON・YAMLはPrettier、PythonはRuffを実行してからPRにする。[整形手順](formatting.md)に従う。

## 設計と食い違ったとき

1. 実装を止め、Issueに「どの記述とどの記述が食い違うか」を書く。どちらかを黙って採用しない。
2. 機械的な整理（依存の書き漏れ、名前の不一致）は、[決定記録](../docs/design/decisions.md)に「確定」として追記し、パケットを直すPRを出す。
3. 製品としての選択（何を必須にするか、閾値、対応範囲）は、Issueにオーナー向けの案と理由を書き、決定記録に「暫定」で追記するPRを出す。そのPRのマージをオーナーの同意とみなし、マージ後はその案で進めてよい（確定で変わりうることをPRに書く）。マージ前は、その項目に関わる実装を進めない。
4. 決定を変えるときは、決定記録の変更をPRにし、影響するIssueを列挙する。

## 手戻りを生む典型と防止

| 起きたこと                                                   | 防止                                                          |
| ------------------------------------------------------------ | ------------------------------------------------------------- |
| 同じ機能を別PRが重複して実装した（先に入った実装と競合した） | 着手前チェック1。着手時にIssueへ担当とブランチを書く          |
| 追い越された古いDraftが残り続けた                            | 長く動かないDraftは、現行mainとの差分を確認して継承かクローズ |
| Issue同士の依存や用語が食い違っていた                        | 着手前チェック2〜4。食い違いは決定記録へ                      |
| テストが古い仕様を前提にして失敗した                         | 古い前提を持ち込まない。仕様変更の理由を確認する              |
| 未解決のリスクを残したままPRが完了扱いになった               | PR本文のチェックと残るリスクを、マージ前に全て解消する        |
| 整形の確認がPRごとに失敗した                                 | 触ったファイルを整形してからPRにする                          |

## 完了の基準

[作業フロー](workflow.md)の「終了」「CIと自己レビュー」「マージ」を満たし、PR本文に次を書きます: 変更したパケット・設計正本、実行した検証（コマンド・対象・結果）、実行していない検証（実GPU・実素材・GUI）、残る要決定。未実行の検証を確認済みと書きません。
